Why I built Anabasis

G. Michael Rapp, November 27, 2026

I research alone, and drafting is the hardest part of the work for me. Anabasis began as a tool to make that part easier for one writer. In under a week it went through 35 releases and became something I’m willing to hand to strangers. This is how it got there, and why each step happened.

The idea November 2026

One file, one writer

I wanted a lightweight word processor and note-taking tool that lived in a single HTML file, built from open-source parts. The first list was short: write and format documents, take and compile notes, save to JSON, export a PDF, and cite sources properly, Chicago first and other guides after. I called it Commonplace.

A few rules went in early, and they haven’t moved:

  • One file. You can download it, open it from your own disk, and keep it. The size budget grew from about 3 MB to 6 MB and finally to 25 MB, but only for features that earned the room.
  • Offline and private. No account, no server, no tracking. It goes online only when you ask it to look something up or back up your work.
  • No AI. Its helpers are scripts and word lists you can read.
  • One project at a time. It’s a desk for the book or paper in front of you, not a library of everything you’ve ever written.

The name changed once the tool had a shape. Xenophon’s Anabasis is the account of a long march home, written by a man who was there. Writing from sources is a long march too, and the app’s map-sheet look, its lambda icon and most of its vocabulary come from that book.

1.0 to 1.9 Nov. 22 to 24

Making the basics trustworthy

Each addition came from something I needed while writing: Word export with real footnotes, a binder that compiles chapters into a manuscript, figures and tables, margin notes, locked project files and optional autosave. I held back a PDF reader at first to keep the file small. That was the compromise for the time being.

I published version 1.0.0 on GitHub on November 22, under the AGPL, with a hosted copy anyone could open. The point releases after that were about speed and fit. Typing in the source form froze the page on large projects, and the toolbars had to work on any screen, phones included.

Then the 1.x line filled in what serious research writing needs: research marks, threads and claims, so you can see what each passage rests on; 55 citation styles; a research journal with hypotheses and a search log; data that stays in step with the text; and equations that survive a round trip through Word. Version 1.6 was the first I was comfortable sending to friends who research and write, with a What’s new note after each update and a way to send me feedback.

2.0 to 2.9 Nov. 24 to 26

A desk for strangers

Version 2.0 was the one meant for people I don’t know. It added co-writing and review without a server: send a copy, then take the changes back as tracked suggestions. I reorganized the interface around clear signposts, because a stranger can’t lean over and ask me where something is. The same day, Anabasis moved to zerohistory.net/anabasis, with Zero History as its publisher.

Because I research alone, I wanted something to push back on my thinking without handing that thinking to a machine. Socrates is a bank of question stems. It started as a prompt beside your questions and grew into tools to examine a claim, steelman the other side, run a pre-mortem, weigh competing explanations and question a whole draft. The Oracle is a conversation partner in the manner of ELIZA, which I studied. It answers from your own project and never goes online.

Smaller tools came along with them: a plain-file archive, Proofread in 27 languages, a book for print and submission packages. Every feature got a short clip, filmed in the real app, for the product page. I kept the old clips as a showcase instead of replacing them, so you can see how the desk grew.

2.10 to 2.10.2 Nov. 27

Security in layers

Version 2.10 made the reader beside the draft a real reading tool: DRM-free ePubs as well as PDFs, highlights in four colors, quotations dropped into a sentence with their page, reading aloud, and every book reopening where you left off.

Then GitHub’s code scanner flagged 259 possible security problems. We went through them one at a time. Almost all were false alarms, but one was real: a project file built to attack the app could run script inside it. Version 2.10.1 closed that the same day, along with a test that opens a hostile file.

That raised a bigger question: what would it take to keep the app as safe as I can make it? Given the threat environment these days, I want security to be a priority, not an afterthought. The answer was 2.10.2. Only the page’s own scripts can run. The browser refuses unchecked HTML. Saved pages lock themselves down. Locked projects encrypt their PDFs, photos and GitHub token. Photos lose their GPS data, Work offline turns the network off, releases are signed, and the bundled libraries are checked every week against published advisories.

The hardening briefly made typing twice as slow on a 120,000-word project. A typing-speed test caught it before release, and a fix brought the old speed back.

2.11 Nov. 27

The Quartermaster

Version 2.11 started with something I’d noticed. A lot of academic software now keeps an audit of how a piece was written, so a student can show the work is theirs. Grammarly does this, and so do a number of other programs, largely to counter AI-generated text. Did that belong in Anabasis?

I thought it did, on conditions set before any code was written. It had to be honest about what it can’t prove, transparent and private. It could never become a way to attack the app or the person using it. And it had to be scoped as an imperfect audit, not proof. It got a written spec with goals, non-goals and a threat table, and then a name: the Quartermaster, the officer who keeps an honest account of the march.

It’s off until you turn it on. It records no keystrokes. It chains each entry to the one before, so later edits show, and every report says plainly that it shows a process, not proof. I want it to help a student show their work, not to stand in for a teacher’s judgment.

The work All 35 releases

Who made it, and how

I designed Anabasis and directed every decision in it. Claude, Anthropic’s AI model, wrote much of the code with me. The app itself contains no AI, and it never sends your writing to one.

Every release followed the same routine: update the version, changelog, help and wiki together; run all the test suites, 51 of them by 2.11; release through a GitHub workflow that builds, tests and signs the file; then check the download and the website.

A few habits did most of the work. Decide what a feature is for, and what it isn’t, before building it. Write tests that find things, and when one fails for the wrong reason, fix the test instead of skipping it. State limits plainly. And keep what’s built: project files from 2.0 still open in 2.11.

Now 30 days quiet

What happens next

Anabasis now goes quiet for 30 days, barring an emergency. Before I build anything else, I want to hear what writers, researchers and students make of it. If something breaks, or something you need is missing, tell me on GitHub.

G. Michael Rapp
